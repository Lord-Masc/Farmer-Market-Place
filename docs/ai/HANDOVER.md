- FLAG — `VerificationQueue.jsx` detects a 403 by matching the error message string (`'do not have permission'`) because `authedFetch` threw only the backend message, with no status attached. Stage 4 attached `error.status` to `authedFetch` throws (`escrowApi.js`) — the queue can now switch to `err.status === 403`; its own string match is still in place (untouched by Stage 4), follow-up: switch it over.
- FLAG — Stage 4 acceptance is claim-first, not a single DB transaction: offer claim (open → accepted, gated) → escrow order creation (idempotent by key) → agreement insert (`UNIQUE(offer_id)` backstop) → requirement flip → reject competing offers. A crash between the claim and the agreement insert is self-healing on a same-key retry (offer `accepted` + no agreement + key → resumes to order creation; escrow replays the order). A keyless retry after a partial accept gets 409 by design. True atomicity would need a Postgres RPC/transaction — possible Stage 4 hardening follow-up, not done here.
- FLAG — Stage 4 accepting one offer rejects the requirement's other open offers (including stale-but-still-`open` expired ones). This gives `offer.rejected` a real path; if competing offers should stay open instead, it is a 5-line removal in `negotiationService.acceptOffer`.
- Stage 5 migration (FILE ONLY, never applied live): `20261120_group_selling.sql` — `group_buys` (owner, crop, threshold, unit kg/quintal, deadline, status open/closed/cancelled, requirement_id/order_id FKs), `group_buy_participants` (UNIQUE(group_buy_id, user_id), contribution, share set at close), `group_settlements` (UNIQUE(group_buy_id, participant_id), amount_paise, status pending/settled), `requirements.group_buy_id` nullable FK. Apply order: after `20261116` (defines `is_admin()`) and `20261119` (defines `requirements`). RLS note: direct PostgREST reads of participants/settlements see only the caller's own rows (+ owner + admin); the full participants list is served via the API (service role) — see the migration header.
- Stage 5 close semantics: claim-first (order → shares → settlements → gated open→closed claim). Negotiated path reuses the Stage 4 agreement's order (verified: buyer is the owner, quantity equals the pooled total — else 409 GROUP_ORDER_MISMATCH). Direct path creates the order via escrow (stock check, cannot buy own product; optional locked unit_price from a chosen quote). A requirement with no agreement yet + no product_id is a 409 GROUP_NEGOTIATION_PENDING. Close does NOT require the deadline to have passed — threshold only. Replay works ONLY when the caller sends Idempotency-Key `group-buy-close-<groupId>` (the frontend sends it on every close); any other second close is a 409, and nothing is ever duplicated.
- Stage 5 list semantics: `?status=all` returns open + closed (the "All" tab); `?status=mine` means owned-or-joined (the "My groups" tab). Offers on a group requirement must match the pooled quantity exactly (422 otherwise — enforced in `negotiationService.createOffer`). Settlement amounts are integer paise split by largest remainder, so they sum EXACTLY to the order total; `share` is a fraction (contribution/total).
- FLAG — Stage 5 settlements record what each participant OWES toward the pooled order (the group buys as one buyer; the owner pays at checkout). They are not payouts and no money moves in this stage — collection/reconciliation is a later stage. The UI labels them "share of the pooled order total" for exactly this reason.
