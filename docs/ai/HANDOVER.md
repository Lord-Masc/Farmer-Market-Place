Failed-auth logging deliberately NOT wired (would spam the table on bot probes).
- FLAG — `VerificationQueue.jsx` detects a 403 by matching the error message string (`'do not have permission'`) because `authedFetch` threw only the backend message, with no status attached. Stage 4 attached `error.status` to `authedFetch` throws (`escrowApi.js`) — the queue can now switch to `err.status === 403`; its own string match is still in place (untouched by Stage 4), follow-up: switch it over.
- FLAG — Stage 4 acceptance is claim-first, not a single DB transaction: offer claim (open → accepted, gated) → escrow order creation (idempotent by key) → agreement insert (`UNIQUE(offer_id)` backstop) → requirement flip → reject competing offers. A crash between the claim and the agreement insert is self-healing on a same-key retry (offer `accepted` + no agreement + key → resumes to order creation; escrow replays the order). A keyless retry after a partial accept gets 409 by design. True atomicity would need a Postgres RPC/transaction — possible Stage 4 hardening follow-up, not done here.
- FLAG — Stage 4 accepting one offer rejects the requirement's other open offers (including stale-but-still-`open` expired ones). This gives `offer.rejected` a real path; if competing offers should stay open instead, it is a 5-line removal in `negotiationService.acceptOffer`.
